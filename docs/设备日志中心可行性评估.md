# AIOps 平台「设备日志中心」可行性评估

> 评估日期：2026-09-14　　评估方式：代码盘点 + 在 .108 测试服对 4 台 H3C 真机做只读探测
> 结论性质：**可以做，且平台已埋了一半地基；但现有 syslog 模块不可直接复用，属于中等规模新功能。**

---

## 一、结论

**能加，值得加，但不要低估工作量。**

平台里已经有一块 syslog 相关代码（接收端点 + 5 厂商解析引擎 + 落库 + 保留清理），看起来"就差一个页面"。实测之后，真实情况是这块代码**目前跑不通**：

1. **没有接收入口** —— 设备 syslog 走 UDP 514，而平台全程没有任何 UDP 监听；现有的是一个 HTTP 端点，交换机不会往它 POST。
2. **解析规则与真机日志不匹配** —— 拿 4 台 H3C 设备的真实日志喂进现有引擎，**7 个样本全部落进 `unknown` 兜底分支**，接口 UP/DOWN 这类最核心的运维日志连接口名都提取不到。
3. **存储表语义不符** —— 现有 `security_events` 表是面向攻击检测设计的（源目 IP、威胁类型、CVE），放不下设备运行日志（模块、助记符、接口名、设备本地时间）。
4. **前端完全空白** —— 全工程 0 处调用，没有页面、没有菜单。

同时也有明确的好消息：**设备侧从未配置过任何远程日志主机**，接入是"从零开始"，不存在打断现有日志链路的风险；**告警联动逻辑（Trap 那套）已成熟可复用**；**后台守护框架、凭据加密、限流、保留期清理全都有现成的**。

## 二、平台现状盘点（实测）

### 2.1 可复用的地基

| 已有能力 | 位置 | 复用方式 |
|---|---|---|
| 厂商识别 + 解析管线骨架 | `services/syslog_service.py`（5 厂商 + 未知兜底） | 保留管线结构，**重写 H3C 规则** |
| HTTP 接入端点 + 限流 | `routers/syslog.py` + `rate_limit.limit_ingest` | 保留作 TCP/外部转发通道 |
| 落库表 + 复合索引 | `models/p3_security.py::SecurityEvent` | 作为安全事件表的样板 |
| 保留期清理框架 | `services/retention_service.py`（分批删除、可按日调度） | 直接套用 |
| **后台循环守护器** | `services/loop_supervisor.py::start_supervised` | **UDP 服务可直接挂上去，崩溃自动重启** |
| 设备凭据解密 | `services/credential_service.py::reveal_secret` | 批量下发设备配置时用 |
| 告警生成与自动恢复 | `routers/traps.py`（linkDown/linkUp → 建告警 / 自动 resolve） | **逻辑可原样搬到日志侧** |
| 设备批量操作通道 | `tools/remote_agent_mcp.py`（remote-ops） | 用于批量下发 loghost 配置 |

一个架构事实需要点明：**平台目前所有"接收类"能力都是 HTTP 端点，靠外部组件（如 snmptrapd）转发**。Trap 模块的注释写得很清楚——"接收 snmptrapd 转发的 trap 数据"。而部署包里**没有任何 syslog/Trap 转发组件**。也就是说 Trap 和 syslog 这两个模块在生产上目前都**没有真实入口**。

### 2.2 四个缺口

| 缺口 | 现状 | 说明 |
|---|---|---|
| ① 接收入口 | **完全缺失** | 无 UDP 514 监听，设备日志无处可发 |
| ② H3C 解析规则 | **失效** | 见 2.3，实测 0% 识别率 |
| ③ 日志数据模型 | **语义不符** | `security_events` 面向攻防，非运维 |
| ④ 前端页面 | **完全空白** | 无列表、无筛选、无详情、无菜单 |

### 2.3 关键实测发现：现有解析规则对真机日志失效

拿实测抓到的真实日志（及 Comware V7 标准 syslog 转发格式）喂进平台现有 `parse_syslog`：

| 样本 | 现有引擎识别为 | 结果 |
|---|---|---|
| 设备本地缓冲区原样格式 | `unknown` / audit | 失败 |
| syslog 转发格式（管理员登录） | `unknown` / audit | 失败 |
| 接口物理状态 DOWN | `unknown` / audit，**接口名提取不到** | 失败 |
| 接口协议状态 DOWN | `unknown` / audit，**接口名提取不到** | 失败 |
| 认证失败 | `unknown` / audit | 失败 |
| 配置变更审计 | `unknown` / audit | 失败 |
| *对照：引擎"预期"的格式 `%%01SEC/4/PACKET_FILTER`* | `h3c` / policy | 通过 |

**7 个真实样本 0 通过。**

原因是现有 H3C 规则按 `%%<数字><模块>/<级别>/<助记符>` 设计（如 `%%01SEC/4/PACKET_FILTER`），而真机实际输出是 `%%10IFNET/3/PHY_UPDOWN` / `SHELL/5/SHELL_LOGIN` 这类**运维模块**日志。更根本的是设计意图不同：现有引擎假设来的是**安全设备日志**（防火墙/IDS 的 PACKET_FILTER 类），而设备日志中心要处理的是**设备运行日志**（IFNET/SHELL/SSHS/STP/OSPF）。

真机日志长这样（实测原文）：

```
%Sep 14 16:23:21:068 2026 SW2 SHELL/5/SHELL_LOGIN: admin logged in from 192.168.124.108.
<190>Sep 14 16:23:24 2026 SW2 %%10IFNET/3/PHY_UPDOWN: Physical state on the interface GigabitEthernet1/0/1 changed to down.
```

可提取的结构：时间戳（含毫秒）、主机名、`模块/级别/助记符`、接口名、用户、源 IP。其中 `/3/` `/5/` 就是日志级别（0-7，与 syslog severity 同序），**分级应以此为准，而不是 PRI 字段**（H3C 的 PRI 由 info-center 全局配置决定，与单条消息的实际级别不一致——实测 PRI=190 解析出 severity=6，而消息内是 3）。

## 三、关键技术决策

### 决策 1：日志从哪里进来

两个选项：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 后端内置 UDP 514 监听**（推荐） | 无外部依赖，开箱即用；复用 `loop_supervisor` 自愈；生产单机部署最干净 | 需处理端口占用与防火墙；Linux 下绑 514 需提权配置 |
| B. 外部 syslog 转发组件 → HTTP 端点 | 复用现有端点，不动端口 | 生产（Windows 单机）要额外安装维护 syslog-ng/rsyslog，违背"一键部署"定位 |

**建议 A**，并把端口做成可配置（默认 514，冲突时可改）。

落地细节（两个平台差异，容易踩）：
- **Windows**：绑定 514 不需要管理员权限，但需放行防火墙 UDP 入站。
- **Linux**：514 < 1024，需要 root 或给服务加 `AmbientCapabilities=CAP_NET_BIND_SERVICE`（在 systemd unit 里加，不必整个服务跑 root）。这正是平台现有 `install.sh` 生成 unit 的地方，改动很小。

### 决策 2：日志存哪里

**建议新建 `device_logs` 表，不复用 `security_events`。** 理由：

- **语义不同**：一个是"设备说了什么"（运维），一个是"攻击者做了什么"（安全）。
- **字段不同**：需要 facility / 模块 / 助记符 / 原始级别(0-7) / 接口名 / 设备本地时间戳 / 接收时间戳 / 原始报文。
- **保留期不同**：等保要求网络日志留存 6 个月；安全事件的保留期策略可能随攻防需求调整，不应相互绑死。
- **增长速度不同**：设备运行日志量级远大于安全事件。

### 决策 3：与现有「安全事件」模块的关系

**建议一个入口、两条落库路径**：UDP 监听收到日志 → 解析 → 按内容分流。

- 含攻击特征的（PACKET_FILTER 等）→ 继续走 `security_events`，供现有安全面板使用
- 设备运行类（接口/协议/登录/配置变更）→ 进 `device_logs`

好处：只监听一个端口，不产生两套采集链路，也不与现有安全模块打架。

### 决策 4：数据量与存储策略

测试设备（仿真环境、刚启动 7 小时）日志量极小，**不能用来推算生产**。按生产 90 台真实设备保守估算：

| 项 | 估算 |
|---|---|
| 单设备日均 | 300~800 条（接入层偏少、核心/出口偏多） |
| 全网日均 | 约 **3~7 万条** |
| 月增 | 约 100~200 万条 |
| 6 个月累计 | 约 **600~1200 万条** |
| 折算存储（均 300B/条 + 索引） | **约 3~6 GB** |

**这个量级很小，PostgreSQL 完全能扛。** 但仍建议：

- **按月分区**（PG 原生 partition）：删除过期数据变成 DROP PARTITION，秒级完成，避免大表 DELETE 的膨胀问题。
- **批量入库**：绝不可每条日志一次 commit。用内存队列攒批（如 500 条或 2 秒 flush）。这是 1000 万条量级下唯一可行的写入方式。
- **保留期默认 180 天**，正好对齐等保六个月要求，且与现有 `SECURITY_EVENTS_DAYS = 180` 一致。

需要防的极端情况：**设备环路/广播风暴时，单台设备可在数秒内产生上万条日志**。必须设置接收侧限流与丢弃计数（现有 `rate_limit` 有样板），否则会把数据库和前端一起拖死。

## 四、等保合规价值（这是本次最实的收益）

《网络安全法》第二十一条要求"按照规定留存相关的网络日志不少于六个月"；等保 2.0 三级的安全审计条款同样要求对网络设备的重要操作与安全事件做审计记录留存。

现状：**平台没有任何设备侧日志留存能力**。设备本地日志缓冲区实测只有 512 条（`Max buffer size: 1024 / Actual 512`），设备一重启就全丢。这意味着**没有日志留存的技术手段，对应条款是空的**。

上日志中心之后直接补上的控制项：
- 网络设备日志集中留存 ≥ 6 个月（默认 180 天，可调）
- 管理员登录/登出/命令执行审计（实测真机日志里 `SHELL_LOGIN` / `SHELL_CMD` / `SHELL_LOGINFAIL` 完整具备）
- 配置变更审计（`SHELL_CMD` 里含完整命令行）
- 认证失败告警（`SHELL_LOGINFAIL` 可联动告警）

这一点比"排查故障方便"更值得作为立项理由。

## 五、工作量分解

| # | 工作项 | 规模 | 说明 |
|---|---|---|---|
| 1 | UDP 接收服务 + 内存队列 + 批量入库 | 中 | 复用 `loop_supervisor`；含限流与丢弃统计 |
| 2 | 解析规则（通用 RFC3164/5424 + H3C Comware） | 中 | 现有骨架保留，规则层重写；含安全/运维分流 |
| 3 | 数据模型 + 按月分区 + 保留策略 | 小 | 套用 `retention_service` |
| 4 | 查询 API（多条件筛选 / 关键字搜索 / 导出 / 统计） | 中 | 现有 syslog 查询接口可作起点 |
| 5 | 前端页面（列表 / 筛选 / 详情 / 实时滚动） | 中 | 纯新增 |
| 6 | 设备侧批量下发 loghost + 回滚 | 中 | 复用 remote-ops；涉及真实配置变更，需回滚能力 |
| 7 | 与告警联动（链路 UP/DOWN、认证失败） | 小 | 逻辑从 `traps.py` 移植 |
| 8 | 测试与真机验证 | 中 | 建议覆盖日志风暴与丢弃场景 |

整体属**中等规模功能**，建议按"P0 打通链路 → P1 运维增强 → P2 智能化"三期走，不要一次全铺开。

## 六、风险与坑

| # | 风险 | 应对 |
|---|---|---|
| 1 | **UDP 无连接、会丢包** | 日志中心定位是"审计与排障"，可接受；对不能丢的审计日志可额外开启 TCP 514 |
| 2 | **日志风暴** | 接收侧限流 + 按设备/模块的采样，丢弃要计数并可观测 |
| 3 | **设备时钟时区** ⚠️ | 实测设备 `display clock` 返回 **UTC**（`16:24:57 UTC`），而平台界面是本地时间（GMT+8）。若直接按设备时间戳入库，会出现 **8 小时偏差**。必须在解析层明确时区处理策略 |
| 4 | **端口占用** | 生产是 Windows 单机，514 可能被其他软件占用 → 端口必须可配置，启动失败要留明确日志 |
| 5 | **存储增长** | 按月分区 + 180 天保留 + 定期清理，避免大表膨胀 |
| 6 | **批量下发 loghost 是真实配置变更** | 必须先备份、支持回滚、分批灰度；建议先在少量设备试 |
| 7 | **生产版本落差** | 生产当前是 v4.4.5，日志中心会落在后续版本，需规划升级路径 |
| 8 | **`generate_sample_logs` 的存在是个信号** | 该接口用于造演示数据。若日志中心上线，需明确它能被关掉，避免演示数据混入真实审计数据（等保场景下这是硬伤） |

## 七、分期建议

**P0 —— 打通链路（先能收、能看）**
- UDP 接收 + 批量入库 + H3C 解析规则 + `device_logs` 表 + 基础查询界面 + 设备侧配置下发（含回滚）
- 验收标准：真机日志能持续入库，接口 UP/DOWN、登录、配置变更可检索

**P1 —— 运维增强**
- 告警联动（链路 DOWN、认证失败 → 告警；UP/成功 → 自动恢复）
- 实时滚动视图、多条件组合筛选、导出
- 日志统计看板（按设备/模块/级别）

**P2 —— 智能化**
- 异常日志模式识别、日志聚类降噪
- 与平台现有 AI 服务结合做根因分析
- 与配置基线核查联动（配置变更日志 → 触发基线复核）
